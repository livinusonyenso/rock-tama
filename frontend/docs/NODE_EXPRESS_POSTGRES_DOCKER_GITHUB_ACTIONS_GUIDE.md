# ROCK-TAMA: Node.js, Express, PostgreSQL, Docker Compose and GitHub Actions

**Step-by-step learning guide · 18 November 2026**

This document contains files to create and commands to run **when you are ready to implement the backend**. Creating this guide does not install packages, create a database, change the working website, push to GitHub or deploy anything.

Keep the existing Next.js frontend. Add an Express API in `api/` and PostgreSQL alongside it. Start with infrastructure and health checks; then move real account, order and payment responsibilities into the API in small steps.

## 1. Understand what you are building

```text
Browser: http://localhost:3000
        |
        v
Next.js frontend: web:3000
        |  server-side requests, API_INTERNAL_URL
        v
Express API: api:4000
        |
        v
PostgreSQL: db:5432
```

Compose also runs a short-lived `migrate` container before starting the API. It applies database changes and exits; it is not a fourth permanent web service.

| Piece | Responsibility |
|---|---|
| Next.js | Existing pages, UI, forms and same-origin browser entry points |
| Express | Future authentication, permissions, customer profiles, orders and payment workflows |
| PostgreSQL | Durable application records, sessions and email-delivery jobs |
| Dockerfiles | Instructions for building application images |
| Compose | Starts the services, network, environment and persistent volumes together |
| GitHub Actions | Runs checks automatically on pull requests and pushes; the workflow below does not deploy |

Inside a container, `localhost` means **that container**, not your Mac or another container. The API connects to hostname `db`; Next.js connects to hostname `api`. Your browser uses published localhost ports.

Do not put `http://api:4000` into a `NEXT_PUBLIC_*` variable. That address is for server-to-server traffic, not the browser.

```json file=api/package.json
    "test": "node --test test/unit/*.test.mjs",
    "test:integration": "node --test test/integration/*.test.mjs"
  }
}
```

Then install into **the API package**, not the frontend:

```bash
npm install --prefix api express@5 pg helmet
```

- `express`: HTTP routing and middleware.
- `pg`: PostgreSQL connection pool and queries.
- `helmet`: useful HTTP response headers.
- Node's built-in watch mode and test runner avoid adding development libraries at this stage.

Commit `api/package-lock.json` after installation. Docker and CI will use `npm ci` to reproduce it. The package file above intentionally gains its dependency versions when you run this command. [Express installation reference](https://expressjs.com/en/5x/starter/installing/).

## 5. Add the API server

Create `api/src/app.mjs`:

```js file=api/src/app.mjs
import express from 'express';
import helmet from 'helmet';

export function createApp({ db }) {
  const app = express();
  app.disable('x-powered-by');
  app.use(helmet());
  app.use(express.json({ limit: '32kb' }));

  app.get('/health/live', (_request, response) => {
    response.json({ status: 'ok' });
  });

  app.get('/health/ready', async (_request, response) => {
    try {
      const result = await db.query(
        'SELECT value FROM public.app_metadata WHERE key = $1',
        ['schema_version'],
      );
      if (!result.rows[0]) throw new Error('Schema not ready');
      response.json({ status: 'ok', database: 'ready' });
    } catch {
      response.status(503).json({ status: 'not_ready' });
    }
  });

  app.use((error, _request, response, next) => {
    if (response.headersSent) return next(error);
    const status = error.status === 400 ? 400 : 500;
    response.status(status).json({ error: status === 400 ? 'Invalid request' : 'Request failed' });
  });

  return app;
}
```

Liveness asks whether the process can answer HTTP. Readiness asks whether it can access the migrated database. These are deliberately different checks. Parameterized queries keep values separate from SQL; use this pattern for future user input too.

Create `api/src/db.mjs`:

```js file=api/src/db.mjs
import { Pool } from 'pg';

if (!process.env.DATABASE_URL) throw new Error('DATABASE_URL is required');

export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  connectionTimeoutMillis: 5000,
  idleTimeoutMillis: 30000,
  query_timeout: 5000,
});

pool.on('error', () => console.error('Unexpected database pool error'));
```

Create `api/src/server.mjs`:

```js file=api/src/server.mjs
import { createApp } from './app.mjs';
import { pool } from './db.mjs';

const port = Number(process.env.PORT || 4000);
const server = createApp({ db: pool }).listen(port, '0.0.0.0', () => {
  console.log(`ROCK-TAMA API listening on port ${port}`);
});

let stopping = false;
function shutdown() {
  if (stopping) return;
  stopping = true;
  const timeout = setTimeout(() => process.exit(1), 10000);
  timeout.unref();
  server.close(async () => {
    try {
      await pool.end();
      process.exit(0);
    } catch {
      process.exit(1);
    }
  });
}
process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```

Bind to `0.0.0.0` **inside** the container so Docker can reach the process. Host port publishing will still be restricted to localhost below.

## 6. Add a migration, rather than creating tables on every request

Create `api/migrations/001_initial.sql`:

```sql file=api/migrations/001_initial.sql
CREATE TABLE public.app_metadata (
  key text PRIMARY KEY,
  value text NOT NULL
);

INSERT INTO public.app_metadata (key, value)
VALUES ('schema_version', '1');
```

This initial table is infrastructure metadata, not pretend users or orders. Add real business tables in subsequent numbered migrations after agreeing on their data contracts.

Create `api/src/migrate.mjs`:

```js file=api/src/migrate.mjs
import { readdir, readFile } from 'node:fs/promises';
import { createHash } from 'node:crypto';
import { fileURLToPath } from 'node:url';
import { pool } from './db.mjs';

const folder = new URL('../migrations/', import.meta.url);
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query('SELECT pg_advisory_xact_lock($1)', [317215]);
  await client.query(`
    CREATE TABLE IF NOT EXISTS public.schema_migrations (
      name text PRIMARY KEY,
      checksum text NOT NULL,
      applied_at timestamptz NOT NULL DEFAULT now()
    )
  `);
  const files = (await readdir(fileURLToPath(folder)))
    .filter(name => /^\d+.*\.sql$/.test(name)).sort();
  for (const name of files) {
    const sql = await readFile(new URL(name, folder), 'utf8');
    const checksum = createHash('sha256').update(sql).digest('hex');
    const existing = await client.query(
      'SELECT checksum FROM public.schema_migrations WHERE name = $1', [name],
    );
    if (existing.rows[0]) {
      if (existing.rows[0].checksum !== checksum) throw new Error(`Applied migration changed: ${name}`);
      continue;
    }
    await client.query(sql);
    await client.query(
      'INSERT INTO public.schema_migrations (name, checksum) VALUES ($1, $2)',
      [name, checksum],
    );
    console.log(`Applied migration: ${name}`);
  }
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
  await pool.end();
}
```

The same checked-out database client runs the whole transaction. The lock serializes simultaneous migration attempts; checksums reject editing an already-applied migration. Add a new file for later changes. This small runner supports transactional migrations; operations such as `CREATE INDEX CONCURRENTLY` need a deliberately separate non-transactional process later. [node-postgres transaction guidance](https://node-postgres.com/features/transactions).

## 7. Add tests before connecting business features

Create `api/test/unit/app.test.mjs`:

```js file=api/test/unit/app.test.mjs
import test from 'node:test';
import assert from 'node:assert/strict';
import { createApp } from '../../src/app.mjs';

async function start(t, db) {
  const server = createApp({ db }).listen(0, '127.0.0.1');
  await new Promise(resolve => server.once('listening', resolve));
  t.after(async () => {
    server.closeAllConnections();
    await new Promise(resolve => server.close(resolve));
  });
  return `http://127.0.0.1:${server.address().port}`;
}

test('liveness answers even when the database is unavailable', async t => {
  const base = await start(t, { query: async () => { throw new Error('offline'); } });
  const response = await fetch(`${base}/health/live`);
  assert.equal(response.status, 200);
  assert.equal((await response.json()).status, 'ok');
});

test('readiness fails without the migrated database', async t => {
  const base = await start(t, { query: async () => { throw new Error('offline'); } });
  const response = await fetch(`${base}/health/ready`);
  assert.equal(response.status, 503);
});

test('readiness succeeds when schema metadata is available', async t => {
  const base = await start(t, { query: async () => ({ rows: [{ value: '1' }] }) });
  assert.equal((await fetch(`${base}/health/ready`)).status, 200);
});
```

Create `api/test/integration/database.test.mjs`:

```js file=api/test/integration/database.test.mjs
import test from 'node:test';
import assert from 'node:assert/strict';
import { pool } from '../../src/db.mjs';

test('migrations are applied to a real PostgreSQL database', async () => {
  try {
    const result = await pool.query(
      'SELECT value FROM public.app_metadata WHERE key = $1', ['schema_version'],
    );
    assert.equal(result.rows[0]?.value, '1');
    const migration = await pool.query(
      'SELECT checksum FROM public.schema_migrations WHERE name = $1', ['001_initial.sql'],
    );
    assert.match(migration.rows[0]?.checksum || '', /^[a-f0-9]{64}$/);
  } finally {
    await pool.end();
  }
});
```

Run the dependency-independent syntax checks and HTTP unit tests after installation:

```bash
npm --prefix api run check
npm --prefix api test
```

The integration test needs a running database and migrations; run it inside the development container in step 13.

## 8. Give the application its own database role

Create `infra/postgres/init/01-app-role.sh`:

```bash file=infra/postgres/init/01-app-role.sh
#!/usr/bin/env bash
set -euo pipefail

psql --set=ON_ERROR_STOP=1 \
  --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" \
  --set=app_user="$APP_DB_USER" \
  --set=app_password="$APP_DB_PASSWORD" \
  --set=database="$POSTGRES_DB" <<'SQL'
CREATE ROLE :"app_user" LOGIN PASSWORD :'app_password';
GRANT CONNECT ON DATABASE :"database" TO :"app_user";
GRANT USAGE, CREATE ON SCHEMA public TO :"app_user";
SQL
```

Then:

```bash
chmod +x infra/postgres/init/01-app-role.sh
```

The database administrator bootstraps the application role. Express uses that application role, not the superuser. The starter role also owns migrations; before public production, separate the migration role from the runtime role so HTTP requests do not need schema-changing privileges.

PostgreSQL initialization scripts run only for an **empty** data directory. Changing this script or an environment password does not reinitialize an existing volume. See the [official PostgreSQL image documentation](https://hub.docker.com/_/postgres).

## 9. Generate local Docker environment variables

Create `scripts/create-docker-env.mjs`:

```js file=scripts/create-docker-env.mjs
import { randomBytes } from 'node:crypto';
import { writeFileSync } from 'node:fs';

const contents = [
  'POSTGRES_USER=postgres',
  'POSTGRES_DB=rocktama',
  `POSTGRES_PASSWORD=${randomBytes(24).toString('hex')}`,
  'APP_DB_USER=rocktama_app',
  `APP_DB_PASSWORD=${randomBytes(24).toString('hex')}`,
  'WEB_PORT=3000',
  'API_PORT=4000',
  'DB_PORT=15432',
  '',
].join('\n');

writeFileSync('.env.docker', contents, { flag: 'wx', mode: 0o600 });
console.log('Created ignored .env.docker. Existing files are never overwritten.');
```

Run it from the repository root:

```bash
node scripts/create-docker-env.mjs
```

It intentionally fails if `.env.docker` already exists. Keep the existing file instead of generating new passwords for an initialized database. Generated passwords are hexadecimal, so they can safely appear in the example connection URL without extra URL encoding. Arbitrary replacement passwords would need URL encoding.

Preserve your existing Paystack test credentials in `.env.local`. Ensure that file exists without overwriting it:

```bash
test -f .env.local || touch .env.local
git check-ignore .env.docker .env.local
```

Only non-secret settings/templates belong in Git. Never copy your actual payment keys into Compose YAML, Dockerfiles or this document.

Create the root `Dockerfile`:

## 11. Create `compose.yml`

Create this at the repository root:

```yaml file=compose.yml
name: rocktama

services:
  db:
    image: postgres:18-bookworm
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?Set POSTGRES_USER}
      POSTGRES_DB: ${POSTGRES_DB:?Set POSTGRES_DB}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD}
      APP_DB_USER: ${APP_DB_USER:?Set APP_DB_USER}
      APP_DB_PASSWORD: ${APP_DB_PASSWORD:?Set APP_DB_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql
      - ./infra/postgres/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
      interval: 5s
      timeout: 5s
      retries: 20
      start_period: 10s
    restart: unless-stopped

  migrate:
    build:
      context: ./api
      target: runtime
    image: rocktama-api-migrate:local
    environment:
      DATABASE_URL: postgresql://${APP_DB_USER}:${APP_DB_PASSWORD}@db:5432/${POSTGRES_DB}
    depends_on:
      db:
        condition: service_healthy
    command: ["npm", "run", "migrate"]
    restart: "no"

  api:
    build:
      context: ./api
      target: runtime
    image: rocktama-api:local
    init: true
    environment:
      NODE_ENV: production
      PORT: "4000"
      DATABASE_URL: postgresql://${APP_DB_USER}:${APP_DB_PASSWORD}@db:5432/${POSTGRES_DB}
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:4000/health/ready').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 10s
    restart: unless-stopped

  web:
    build:
      context: .
      target: runtime
    image: rocktama-web:local
    init: true
    env_file:
      - .env.local
    environment:
      NODE_ENV: production
      DEPLOY_MODE: staging
      HOSTNAME: 0.0.0.0
      PORT: "3000"
      API_INTERNAL_URL: http://api:4000
    ports:
      - "127.0.0.1:${WEB_PORT:-3000}:3000"
    volumes:
      - web_data:/app/.data
    depends_on:
      api:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 15s
      timeout: 10s
      retries: 12
      start_period: 30s
    restart: unless-stopped

volumes:
  pg_data:
  web_data:
```

### What the important lines mean

| Setting | Explanation |
|---|---|
| `build.context` | Folder Docker can read while building that image |
| `target` | Named stage selected from the Dockerfile |
| `environment` | Variables supplied to the running container |
| `${VARIABLE}` | Compose substitutes a value from the shell/explicit environment file |
| `$${VARIABLE}` | Leaves substitution for the shell inside the container |
| `depends_on: service_healthy` | Waits for a dependency's readiness health check |
| `service_completed_successfully` | Waits until the migration job exits successfully |
| `pg_data` | Persistent named volume for database files |
| `web_data` | Temporary bridge for existing local file-based enquiry/receipt storage |
| `:ro` | Read-only bind mount |
| `127.0.0.1:...` | Publishes only on your machine, not every network interface |

The PostgreSQL 18 image stores its version-specific data beneath `/var/lib/postgresql`, so the volume mounts that parent path. Do not substitute the old `/var/lib/postgresql/data` example from older image guides. [Official image layout](https://hub.docker.com/_/postgres).

A startup order alone does not mean a database is ready; health conditions and the migration job provide that gate. The application must still handle later database outages. [Docker dependency/readiness reference](https://docs.docker.com/compose/how-tos/startup-order/).

### Validate and start

```bash
docker compose --env-file .env.docker config --quiet
docker compose --env-file .env.docker up --build -d --wait
docker compose --env-file .env.docker ps -a
```

`migrate` should show `Exited (0)`. The other three services should become healthy. If migration fails, inspect it before proceeding:

```bash
docker compose --env-file .env.docker logs --tail=100 migrate api db
```

Open `http://localhost:3000`. If you changed `WEB_PORT`, use that port instead.

Prefer `config --quiet`: plain `docker compose config` expands environment values and may print credentials. Do not share that expanded output.

```json
{"status":"ok","database":"ready"}
```

If you changed `API_PORT`, adjust the curl URL. The database is available to local tools at `localhost:15432`, while the container connection URL still uses `db:5432`.

For the rest of development, consistently include **both** `-f` options. Omitting the development file can recreate services in the base runtime configuration.

## 14. Connect Next.js to the API without exposing an internal hostname

As a small first integration, create `app/api/backend/health/route.ts`:

```ts file=app/api/backend/health/route.ts
import { connection } from 'next/server';

export async function GET() {
  await connection();
  const base = process.env.API_INTERNAL_URL;
  if (!base) return Response.json({ error: 'API unavailable' }, { status: 503 });
  try {
    const upstream = await fetch(`${base}/health/ready`, {
      cache: 'no-store',
      signal: AbortSignal.timeout(5000),
    });
    if (!upstream.ok) return Response.json({ error: 'API not ready' }, { status: 503 });
    return Response.json(await upstream.json(), {
      headers: { 'Cache-Control': 'no-store' },
    });
  } catch {
    return Response.json({ error: 'API unavailable' }, { status: 503 });
  }
}
```

Check the entire path:

```bash
curl --fail http://localhost:3000/api/backend/health
```

The browser calls the Next.js origin; Next.js calls the internal Express service. This demonstration needs no browser CORS configuration. Add future authenticated routes deliberately; do not turn this into an unrestricted proxy that forwards arbitrary paths, headers or cookies.

Do not overwrite existing `/api/payments/...` handlers. They currently verify payments and issue receipts, and remain the owners of those responsibilities until a planned cutover.

## 15. Create GitHub Actions CI

Only add this workflow after the preceding files and **both lockfiles** are committed. Create `.github/workflows/ci.yml`:

```yaml file=.github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  frontend:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      DEPLOY_MODE: staging
      PAYSTACK_SECRET_KEY: ""
      ENQUIRY_DELIVERY: dev-file
      NEXT_TELEMETRY_DISABLED: "1"
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: "24"
          cache: npm
          cache-dependency-path: package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm run build
      - run: npx tsc --noEmit

  api:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    env:
      NODE_ENV: test
      DATABASE_URL: postgresql://ci_runner:ci_only_password@127.0.0.1:5432/rocktama_ci
    services:
      postgres:
        image: postgres:18-bookworm
        env:
          POSTGRES_USER: ci_runner
          POSTGRES_PASSWORD: ci_only_password
          POSTGRES_DB: rocktama_ci
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -h 127.0.0.1 -U ci_runner -d rocktama_ci"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 20
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: "24"
          cache: npm
          cache-dependency-path: api/package-lock.json
      - run: npm ci --prefix api
      - run: npm --prefix api run check
      - run: npm --prefix api test
      - run: npm --prefix api run migrate
      - run: npm --prefix api run test:integration

  containers:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: "24"
      - run: node scripts/create-docker-env.mjs
      - run: touch .env.local
      - run: docker compose --env-file .env.docker config --quiet
      - run: docker compose --env-file .env.docker -f compose.yml -f compose.dev.yml config --quiet
      - run: docker compose --env-file .env.docker build
      - run: docker compose --env-file .env.docker up -d --wait --wait-timeout 180
      - name: Verify frontend-to-database path
        run: curl --fail --retry 5 --retry-delay 2 --retry-connrefused http://localhost:3000/api/backend/health
      - name: Container logs on failure
        if: failure()
        run: docker compose --env-file .env.docker logs --no-color --tail=100
      - name: Stop CI stack
        if: always()
        run: docker compose --env-file .env.docker down --volumes
```

The hardcoded CI database password is for a disposable test database, not a production secret. The isolated CI runner removes its own throwaway volumes in the final step; do not copy that cleanup command into your normal local shutdown routine.

The frontend build uses the normal project build, not a diagnostic Webpack workaround. CI explicitly uses staging and no real payment key; provider acceptance and production readiness are separate checks. The container job builds and boots the actual Compose topology, including migrations and the frontend proxy.

Action major tags are readable for learning and were checked against their official usage documentation; for a hardened workflow, pin reviewed commit SHAs and maintain them with Dependabot. [Checkout action](https://github.com/actions/checkout), [setup-node action](https://github.com/actions/setup-node), [GitHub PostgreSQL services](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

No deployment or image publishing occurs. Add a separate deployment workflow after choosing the hosting target, registry, environment approvals and rollback process. Do not place production credentials into a pull-request workflow or run untrusted PR code through `pull_request_target` with secrets.

## 16. Everyday Docker commands

| Task | Command / guidance |
|---|---|
| Show state | `docker compose --env-file .env.docker ps -a` |
| Follow API logs | `docker compose --env-file .env.docker logs -f api` |
| Stop without losing data | `docker compose --env-file .env.docker down` |
| Start a runtime stack again | `docker compose --env-file .env.docker up -d --wait` |
| Develop with hot reload | Use both `-f compose.yml -f compose.dev.yml` flags |
| Install a new API dependency | Run `npm install --prefix api <package>`, commit its lockfile, rebuild the API image |
| Apply changed environment | Recreate the relevant service; restarting alone does not reload `env_file` values |

Example after changing `.env.local` in development:

```bash
docker compose --env-file .env.docker -f compose.yml -f compose.dev.yml up -d --force-recreate web
```

A named volume survives container recreation. It is **not a backup**. To take a local backup:

```bash
mkdir -p backups
docker compose --env-file .env.docker exec -T db pg_dump -U postgres -d rocktama -Fc > backups/rocktama.dump
```

Use a fresh scratch database to test restoration, rather than overwriting the working database:

```bash
docker compose --env-file .env.docker exec db createdb -U postgres rocktama_restore_check
docker compose --env-file .env.docker exec -T db pg_restore -U postgres -d rocktama_restore_check --no-owner --no-acl < backups/rocktama.dump
```

**Destructive reset, only for data you deliberately want to discard:** `docker compose --env-file .env.docker down --volumes` deletes this project's named volumes, including the database and existing local receipt/enquiry store. Do not run it as a routine fix. Changing a PostgreSQL major image tag is also not an upgrade procedure; plan a tested backup/restore or `pg_upgrade` migration.

## 17. Move existing ROCK-TAMA features in this order

Adding PostgreSQL does not automatically move current cookies or file stores into it. The bootstrap above has no real login/order API yet.

1. **Accounts and profiles:** agree the Express API contract; implement password hashing, secure sessions and logout; persist users and delivery addresses. Derive identity/roles on the server. Registration must not grant admin or approved distributor access. Replace demo login and signed-in checkout's temporary profile cookie with the real authenticated profile.
2. **Orders:** create orders/order-items in PostgreSQL and snapshot unit prices in integer kobo. Keep addresses linked to their owning user and snapshot the delivery address for each order. Keep guest checkout supported if still desired.
3. **Payments:** make Express the single owner of initialization, provider verification and signed webhooks. Store a unique provider/reference pair. Verify amount, currency and outcome; do not trust browser success. Do not keep independent Next.js and Express handlers sending the same notifications.
4. **Receipt delivery:** persist verified payments plus durable receipt-email/outbox jobs in a transaction. Use a unique payment/message-kind key and retries. The current Resend idempotency window is not permanent application-level delivery history.
5. **Receipt downloads:** authorize the real order owner or an explicit guest capability before generating/downloading the receipt. Do not expose arbitrary receipts by bare reference.
6. **Admin UI:** connect authorised endpoints only after server-side permissions exist. Replace sample records with real database queries deliberately, rather than presenting mock records as production orders.

Keep the current frontend UI and working payment verification during this migration. Change one responsibility at a time, with tests before removing its existing owner.

## 18. Before a public production deployment

This guide intentionally supplies a local/staging stack and CI, not an approved production launch.

- Choose where containers will run and where PostgreSQL/backups will live. Use TLS at the public entry point; do not publicly publish the database.
- Replace demo authentication and commercial placeholders; implement real permissions. Use runtime secrets and a separate migration role. Configure production database TLS according to that database provider rather than blindly disabling certificate verification.
- Refactor launch-readiness checks for the Docker hosting environment: some existing checks are conditional on `VERCEL_ENV=production`, so simply running outside Vercel does not prove they ran. Do not inject live secrets into Docker build arguments/layers to satisfy a build guard.
- Build a deliberate production configuration instead of reusing the hardcoded staging Docker image unchanged. Set up immutable image tags/digests, deployment approval, migrations, tested backups and rollback.
- Preserve the project's claim-verification requirements and real payment/email configuration. The previously observed Paystack HTTP403 and missing Resend credentials are not fixed by adding Docker.

These are later implementation steps; this document does not claim that the demo account, admin or payment setup is ready for public production.

## 19. Troubleshooting

| Symptom | Check |
|---|---|
| `port is already allocated` | Stop the existing host service or change `WEB_PORT`, `API_PORT` or `DB_PORT`. Keep internal container ports unchanged. |
| API cannot connect to PostgreSQL | Inside Compose use `db:5432`, not localhost. Check DB health and the migration logs. |
| Password authentication fails after changing `.env.docker` | Existing database roles retain their original passwords. Restore the matching environment or rotate the role password intentionally; do not casually delete the volume. |
| Initialization script changes appear ignored | Init scripts run only on an empty database volume; ongoing changes belong in migrations. |
| New migration does not appear | Rebuild/run the `migrate` service. Hot reload is not migration execution. |
| Frontend cannot reach API | Next server uses `API_INTERNAL_URL=http://api:4000`; browser uses the Next origin. Check `/api/backend/health`. |
| Permission denied writing `.next` or `.data` | Check the Dockerfile ownership and mount configuration; do not solve it with broad `chmod 777`. |
| Frontend build cannot fetch fonts | Check build-network access. Do not permanently rewrite app code or weaken launch checks for an environment restriction. |
| Turbopack worker-port permission error | Compare actual container and host logs. A diagnostic Webpack build is not proof the normal build passed. |
| CI cannot find the API lockfile | Run the API installation step and commit `api/package-lock.json`. |
| CI container test fails but unit tests pass | Inspect migration/readiness logs; unit mocks do not prove the Compose network, database and standalone frontend are wired correctly. |

## 20. Completion checkpoints

Work through these in order:

1. API syntax/unit tests pass on your machine.
2. Compose configuration validates without printing secrets.
3. `migrate` exits0; `db`, `api` and `web` become healthy.
4. `/health/ready` works on the API development port.
5. `/api/backend/health` works through Next.js.
6. Integration tests confirm a real migrated PostgreSQL database.
7. Source edits reload in development; data survives ordinary `down`/`up`.
8. All three GitHub Actions jobs pass after you choose to push the implementation.
9. Only then start real authentication/profile integration.
