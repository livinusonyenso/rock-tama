# Checkout — reference implementation

`/checkout` follows the owner-supplied mockup: static waterfall banner, ivory contact/address panels, delivery/payment panels, forest-green order summary, editable quantities, draft totals, help card and waterfall promise strip. Existing header/footer and catalogue stay shared. `/cart` now links to checkout while retaining its quotation alternative.

The reference's Paystack integration, bank account, promo discount, delivery fees/timelines, payment/security badges and contact details are not configured or approved business data. They are not presented as working services. The final button says **Send order request**. Existing approved draft catalogue prices are used; unknown prices remain on request, delivery additional and subject to quotation. No payment is collected and a sent request is not a paid order. No new dependencies, pricing changes or unsupported scientific claims.

`Checkout` is a client island for local basket subscription, editable quantities and controlled contact fields. Product thumbnails reuse existing gallery assets, including separate 12/24 bottle packs. Inputs have labels, autocomplete, accessible errors, 44px controls and first-error focus. Personal details stay in component memory; only the existing variant IDs/quantities are saved locally. No-JS and empty-basket states offer working shop/enquiry links. A successful request preserves the basket because it is not a completed purchase.

`submitCheckout` validates fields and basket IDs/quantities on the server using Zod. It derives prices from server catalogue data and ignores client totals. Single packs retain existing bottle/carton units; mixed items are itemised and converted to bottles using the draft 12-bottle carton configuration. It reuses the existing enquiry action, honeypot, rate limit and delivery adapter. Success requires actual adapter acceptance; errors retain typed contact details. This is the existing order-enquiry data contract, not a separate payment/order database.
